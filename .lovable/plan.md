# Phase 5 — Risk Score + Emergency Re-balance

## เป้าหมาย
ให้แผนเส้นทางรู้ว่า "ป้ายไหนควรตรวจก่อน" และเมื่อมีคนลา ระบบบอกได้ทันทีว่า
งานที่เหลือหนักขึ้นเท่าไร โดยไม่เรียก AI และไม่เพิ่ม query หนัก

## สรุปตอบคำถาม: ต้องสร้าง table ใหม่ไหม?

**Phase 5 ไม่ต้องสร้าง table ใหม่ใน database** ถ้าทำเฉพาะใน Route Monitoring
เพราะข้อมูลเคลมอยู่ใน `public.claims` แล้ว สามารถนับ claims ย้อนหลัง 30/90 วันจาก table นั้นได้เลย

**ถ้าต้องการให้ Risk Score ใช้ซ้ำในงานอื่นๆ** (เช่น หน้า Asset History, รายงาน Dashboard, การแจ้งเตือน)
ควรสร้าง table ใหม่ชื่อ `asset_risk_scores` หรือ `asset_health_scores` ไว้เก็บคะแนนเฉลี่ยแต่ละป้าย
และจะอัปเดตผ่าน cron/schedule หรือ recalculate เมื่อ sync claims

หากตัดสินใจสร้าง table ใหม่เพื่อใช้ซ้ำ โครงสร้างจะประมาณนี้:
- `asset_old_code` (text) — รหัสป้าย เชื่อมกับ assets
- `risk_level` (text) — HIGH / MEDIUM / LOW / NONE
- `claims_30d` (int) — จำนวนเคลม 30 วัน
- `claims_90d` (int) — จำนวนเคลม 90 วัน
- `open_claims` (int) — จำนวนเคลมที่ยังค้างเปิด
- `last_claim_at` (timestamp) — วันที่เคลมล่าสุด
- `score` (int) — คะแนนความเสี่ยงรวม (เช่น 0-100)
- `updated_at` — อัปเดตล่าสุด

**แนะนำ Phase 5 (ประหยัดเครดิต):** คำนวณจาก `claims` ตอนเปิดหน้า ไม่สร้าง table ใหม่
ถ้าหลังจากใช้งานแล้วต้องการนำไปใช้ซ้ากับหน้าอื่น ค่อยสร้าง table ใน Phase 6 หรือครั้งถัดไป

## ขอบเขต (ไม่ซ้ำกับของที่มีแล้ว)
สิ่งที่มีอยู่แล้วและ **จะไม่สร้างซ้ำ**: toggle "เหตุฉุกเฉิน/คนลา" + ช่องจำนวนคนลา
(ตอนนี้แค่ลดจำนวนคนแล้วคำนวณใหม่), K-Means, แบ่งวัน, OSRM routing, save/load plan,
export, dashboard ภาระงาน, layer/style control
Phase 5 จึงเพิ่มเฉพาะ 2 ก้อน: **คะแนนความเสี่ยงต่อป้าย** และ **แผงผลกระทบเมื่อมีคนลา**

## 1) Risk Score ต่อป้าย
- server function ใหม่ 1 ตัว: ดึงเคลมย้อนหลัง 90 วัน (เฉพาะคอลัมน์รหัสป้าย + วันที่ + สถานะ)
  แล้วสรุปเป็น map: `รหัสป้าย → { เคลม 30 วัน, เคลม 90 วัน, เคลมค้างเปิด }`
  รวมผลบนเซิร์ฟเวอร์ ไม่ส่ง row ดิบมา browser
- เรียกครั้งเดียวต่อการเปิดหน้า (cache 10 นาที) ไม่ผูกกับปุ่ม Run → ไม่เพิ่มภาระตอนคำนวณเส้นทาง
- จัดระดับ: **สูง** = มีเคลมค้างเปิด หรือ ≥1 เคลมใน 30 วัน · **กลาง** = มีเคลมใน 90 วัน ·
  **ต่ำ** = ไม่มีเคลม 90 วัน
- ใช้ผลใน 3 จุด (ของเดิมทั้งหมด ไม่มีหน้าใหม่):
  - เรียงลำดับความสำคัญตอนแบ่งวัน: ป้ายเสี่ยงสูงถูกจัดเข้าวันแรก ๆ ของแต่ละคน
  - แสดง badge ระดับความเสี่ยงในรายการจุดแวะ (แผงขวา + bottom sheet มือถือ)
  - เพิ่มคอลัมน์ระดับความเสี่ยงใน export CSV
- ปิด/เปิดได้ด้วย toggle "จัดลำดับตามความเสี่ยง" (ค่าเริ่มต้น: เปิด) — ถ้าปิด พฤติกรรมเหมือน Phase 4 เดิม

## 2) Emergency Re-balance (ผลกระทบเมื่อคนลา)
- ยังใช้ toggle เดิม แต่เพิ่ม "แผงผลกระทบ" ใต้ฟอร์ม: เทียบก่อน/หลังคนลา
  (ป้าย/คน/วัน, ชั่วโมงต่อวันโดยประมาณ, จำนวนคน-วันที่เกินเพดาน 8 ชม.)
  คำนวณจากค่าเวลาต่อป้าย + ระยะทางประมาณของเดิม (ไม่ยิง OSRM เพิ่ม → 0 ค่าใช้จ่าย)
- ถ้าเกินเพดาน: เตือนสีส้ม + บอกว่ามีป้ายเสี่ยงต่ำกี่ป้ายที่ "เลื่อนได้"
  (แค่แสดงตัวเลข — การตัดออกจริงเป็นงาน Phase 6)

## ผลกระทบต่อการทำงาน
- ไม่แตะ Asset Map / Claim Aging / เมนูอื่น
- ไม่แก้ฐานข้อมูล ไม่มีตารางใหม่ (ตารางป้ายที่ถูกข้ามเป็นของ Phase 6)
- ผู้ใช้เดิมยังทำงานเหมือนเดิม เพราะทุกอย่างใหม่เป็นข้อมูลเสริม + toggle ที่ปิดได้
- ค่าใช้จ่ายเพิ่ม: query aggregate 1 ครั้งต่อการเปิดหน้า, ไม่มีการเรียก AI, ไม่เพิ่มจำนวน request OSRM

## รายละเอียดทางเทคนิค
- ไฟล์ใหม่: `src/lib/route-risk.functions.ts` (server fn aggregate ความเสี่ยง)
- แก้: `src/lib/route-planner.ts` (รับ weight ความเสี่ยงตอน `splitIntoDaysBalanced`),
  `src/routes/route-monitoring.tsx` (toggle, badge, แผงผลกระทบ),
  `src/lib/route-plan-export.ts` (คอลัมน์ความเสี่ยงใน CSV)
- จับคู่ป้าย↔เคลมด้วย `old_code` (คีย์เดียวกับที่ระบบ sync ใช้อยู่)
- ถ้า query ความเสี่ยงล้มเหลว: ถือว่าทุกป้ายเป็น "ไม่ระบุ" และแผนยังคำนวณได้ปกติ
